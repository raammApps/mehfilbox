# Codebase Assessment

A read of Mehfilbox's code as it stood on 15 September 2026: quality, maintainability, scalability, deployability. It draws on four independent adversarial review passes — maintainability, scalability, deployability, documentation — each then re-verified line by line against the repository by a second, skeptical pass. Every finding kept below is one the verifier confirmed real; severities are the verifier's corrected ones where it corrected them, the original reviewer's otherwise. Claims the verifier caught exaggerating are not silently dropped — they're in the Appendix, with the reason.

Related: [00-README.md](00-README.md) for how this set of documents fits together, [03-port-and-build-vs-buy.md](03-port-and-build-vs-buy.md) for what a rewrite would cost against what it would fix, [06-what-changes-next.md](06-what-changes-next.md) for the combined plan across all findings, [07-evidence-and-provenance.md](07-evidence-and-provenance.md) for the reconciled finding counts and what the reviews could not establish.

## 1. The short answer

No — this is not an unmanageable codebase, and "cluttered" isn't really the right word for what's wrong with it. What's wrong is narrower and more fixable than that word implies: two live bugs, a documentation tree that has outgrown its own reading budget, and predictable test debt concentrated in four large admin components. 49 findings were raised across the four lenses and all 49 were confirmed real; six pairs turned out to be the same issue caught independently by two lenses, so the distinct list is **43 entries: 2 high, 18 medium, 23 low**. The raw per-verdict tally before that merge is **3 high / 21 medium / 25 low across 49 verdicts**, because H1 below was raised twice — quote the merged numbers or the raw ones, but say which, since they cannot both be 49 and sum to 43. Both high-severity entries are cheap to fix and both are in §3. None of this looks like the accumulated mess of a codebase nobody understands; it looks like a young, fast-moving codebase where the discipline holds almost everywhere and slips in a few predictable places.

**One scope limit, stated before the numbers are read as a risk picture.** The four lenses were maintainability, scalability, deployability and documentation. **Security was not one of them.** Three named, already-verified production security gaps therefore sit outside every count in this document; they are summarised in §3a and covered in full in [01 §12](01-master-project.md). "2 high severity" is a statement about code health, not about exposure.

Five files out of 296 break 600 lines. The rest of `app/` is right-sized: largest page 357 lines, largest API route 215, most routes under 150, no business logic living in pages.

**What "cluttered" actually is here.** It isn't sprawl — it's concentration. Two driver files (the Supabase and memory repositories) and four admin components (`CreateWizard`, `CustomizerShell`, `ThemeStudio`, `PreviewPane`) hold a disproportionate share of both the size and the risk; the other ~290 files are unremarkable by design. TypeScript strictness is real, not nominal: across ~35,000 lines there is exactly one `as unknown as` (`modules/registry.ts:39`, argued in a comment), zero `@ts-ignore`, zero `@ts-expect-error`, and one file-level eslint-disable, scoped and explained (`lib/db/supabase-repository.ts:41`). `pnpm lint` is clean and 659 unit tests run in 6.6 seconds.

So the honest verdict is: a well-disciplined codebase with two live bugs that need fixing this week, a documentation tree that promises an 8k-token cold start and actually costs ~45k, and a predictable pocket of UI test debt in the screens a studio uses most. §2 sets out what's genuinely good and why that matters for what follows; §3 is the full confirmed-findings list; §3a names what a security lens would have covered and this one did not; §8 answers directly whether a rewrite would fix any of this.

**What this verdict cannot tell you: whether the product meets its own definition of done.** CLAUDE.md sets one bar — a film starts playing "in under a second and a half on 4G" — and **no number exists for it**. The instrument was built: `app/api/qoe/route.ts` takes a playback-start beacon, compares it against `PLAYBACK_START_MS` in `lib/budgets.ts`, and computes an `overBudget` boolean. It then writes that to a structured log nothing reads back — no p75, no dashboard, no alert (`map-guest.md` §7 item 7; the route's own comment quotes the spec's line that "a target nobody measures is a wish"). `docs/NEXT.md`'s N-81 and N-14 both still say the number has never been measured against real footage on a real handset. So four lenses can say the code is disciplined and the media path is architecturally sound (§2, §4); none of them can say the product is fast enough, and nothing in this document should be read as saying so. Closing that is an operator task (one real wedding, one real phone) plus a few hours of reading the logs back — not an engineering finding, which is exactly why no lens raised it.

## 2. What is genuinely good

Four reviewers were told to find problems, and each came back with a strengths list before the findings. These aren't consolation prizes — several are the reason the findings in §3 are as narrow as they are.

**The authorisation seam holds, everywhere, every time.** `lib/catalogue-access.ts` (88 lines, 92% line coverage) is the only place a guest request is authorised; `lib/admin/session.ts` (120 lines) is the only place `org_id` enters a query. **What was checked, precisely:** the repository has 61 `route.ts`/`route.tsx` files under `app/api`, of which **34 sit under `app/api/admin/`** (11 of those under `app/api/admin/platform/`). Every one of those 34 — 46 handlers between them — calls `requireOperator`, `requireOwnedCatalogue`, `requireEditableCatalogue` or `requirePlatformAdmin`, with zero exceptions; the reviewer walked them by hand and the second pass re-walked and confirmed. The guarantee covers those 34 admin route files and the `app/admin/**/page.tsx` pages (which use a different family of guard names — see M5), not all 61: the remaining 27 are the guest and webhook surface, authorised through `lib/catalogue-access.ts` or a bearer secret instead. For a multi-tenant wedding platform where the failure mode is one studio reading another studio's wedding, that is the single most important property in the repository, and at 179 commits it is unusual that it still holds perfectly.

**The module boundary is enforced structurally, not by convention.** `modules/contract.ts` (126 lines) defines the plug-in interface, `modules/registry.ts` (117 lines) is the only wiring point, and `tests/unit/registry.test.ts:123-157` walks the filesystem and fails the build if any file outside `modules/` so much as mentions a module type string. Nine module types exist; there is not one `switch` on module type outside that folder. A rewrite would have to reinvent this test to keep the same guarantee — and would probably not bother.

**Type and lint discipline is real, not nominal.** `tsconfig.json` has `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride` and `noFallthroughCasesInSwitch` all on. Across ~35,000 lines: one `as unknown as` (justified in a comment), zero `@ts-ignore`, zero `@ts-expect-error`, one scoped eslint-disable. `pnpm lint` is clean and 659 tests pass in 6.6 seconds.

**The test suite doesn't lie about itself.** Nothing is hidden behind `.skip` or `.fixme` — every one of the 56 skipped E2E tests is a conditional device guard, not a disabled failure (confirmed by re-reading each one). The pure-logic core — `lib/schema.ts`, `lib/i18n.ts`, `lib/tenant.ts`, `lib/entitlements.ts`, `lib/catalogue-cache.ts` — sits at 92–100% coverage. `tests/unit/supabase-mapping.test.ts` is written in the exact shape of a real production incident (a storage-cap column that silently went unmapped, so the 20GB cap never once fired) with the incident recorded in the file header — the rare case of a team generalising a fix instead of just applying it.

**The media path keeps the application out of the way of the bytes.** Video upload hands the browser a TUS ticket directly (`app/api/admin/uploads/route.ts:122`); playback returns a signed URL, not a proxied stream (`app/api/playback/token/route.ts:57`); posters answer with a redirect to the CDN instead of passing through the server (`app/api/poster/[titleId]/route.ts:66-70`). Photos are the one exception and it's a bounded one — capped at 4MB with the reason on record (`app/api/admin/catalogues/[id]/photos/route.ts:19-31`): the storage-zone write password can't go to the browser, so kilobytes proxy and gigabytes never do. This is the property that makes the unit economics work regardless of implementation language — it bears directly on §8.

**Cache invalidation is complete — the part of a cache that's normally wrong.** `revalidateCatalogue` has 15 call sites covering every write an operator or guest can trigger — publish, edit, retry, transfer, claim, offline changes — plus the Bunny webhook and the reconcile cron. The two deliberate non-invalidations (draft autosave, a frozen published preset) are argued in place, not forgotten.

**Operational tooling is ahead of the product's stage.** `lib/env.ts` validates every configuration key once at boot with cross-field refinements that encode real incidents, so a misconfigured deploy fails at boot instead of on a guest's first playback request. `scripts/preflight.ts` distinguishes a Bunny account key from a library key and round-trips a real photo write → CDN read → delete before every deploy. The synthetic guest check (`app/api/cron/synthetic/route.ts`) walks resolve → load bundle → find a ready film → mint a playback token against real production data on a schedule — better monitoring than most funded startups run at this stage (its own schedule is a separate problem — see §3, H2).

**The in-code documentation is the best documentation in the repository.** `lib/catalogue-access.ts:8-14` states its own invariant; `modules/registry.ts:14-19` states its own contract; comments record rejected alternatives rather than restating code (`lib/entitlements.ts:16-28`, `lib/tenant.ts:4-20`). An engineer who read only the code would come away better informed than one who read only `docs/` — which is a real problem for the documentation tree (§6), but a real strength of the code.

## 3. Confirmed findings, by severity

49 findings were raised across the four lenses; all 49 were confirmed real by the second pass (none were thrown out outright — where the verifier disagreed, it corrected the severity or the evidence rather than rejecting the finding; see the Appendix for the specific claims within findings that didn't hold up). Six pairs of findings turned out to be the same issue caught independently by two lenses — those are merged below into one entry, noted where it happened — so 49 raised verdicts (3 high / 21 medium / 25 low, counting each verdict separately) become 43 distinct entries: 2 high, 18 medium, 23 low. Effort estimates are the reviewer's.

### High severity — 2 findings

**H1. The Supabase driver ignores publish state on the title read path — guests can already see films that haven't been published, and withdrawal may not withdraw.** Caught independently by both the maintainability and scalability reviews. **The photograph half of this finding was fixed on 16 September, mid-review** — see the note at the end of this entry; everything above it is still live.

- *Evidence.* `listTitles({ publishedOnly })` gates on `.eq('published', true).eq('status','ready')` with no `live_at` check (`lib/db/supabase-repository.ts:1392`; the method signature is at :1390). The memory driver deliberately gates on `status === 'ready' && liveAt !== null` instead, with a comment explaining that gating on `published` alone "was the first attempt and it broke withdrawal" (`lib/db/memory-repository.ts:757`). The `live_at` column exists, is written on publish, and is read by the mapper; the schema's own doc-comment says "Null means the couple cannot see it, whatever `published` says" (`lib/schema.ts:461-462`). **The same gap exists a third time, on the playback path:** `POST /api/playback/token` refuses a title on `!title.published` and never looks at `live_at` at all (`app/api/playback/token/route.ts:35-41`), so a ticked-but-not-yet-published film can still mint a working, TTL'd playback URL for anyone who knows its slug — and a slug is derived once from the upload filename and never re-derived on rename (N-84), so it is guessable from a forwarded file (`map-media-infra.md` §7 item 3 flags this as unresolved). No behavioural test covers any of it: `playwright.config.ts:21` and every unit test run against the memory driver; the Supabase driver's only automated contact is a column-mapping test, the query-shape test added on 16 September (below), and an opt-in integration suite that needs `RUN_INTEGRATION=1` and real credentials.
- *Why it matters.* A film a studio has readied but deliberately hasn't published appearing on the couple's live wedding page is a phone call, a possible refund, and potentially a wedding film in front of the wrong audience. This is what N-57 ("content waits for Publish") was built to prevent, and it's fully correct in the driver nobody ships and broken in the one that's live, while the console tells the operator with a straight face that "3 films will go live when you publish." It is live on all 5 production catalogues today, independent of scale.
- *Fix.* Two lines, plus a third site: add the `live_at` predicate to the `publishedOnly` branch at `lib/db/supabase-repository.ts:1392`, and add the same check to the playback-token gate at `app/api/playback/token/route.ts:35-41` — deciding first whether the customizer's own preview needs an operator-scoped exemption, since by CLAUDE.md's documented deviation it mounts the real guest components and calls this same public endpoint. Then close the class of bug, not just the instance: build one contract test suite that runs the same assertions against both `MemoryRepository` and `SupabaseRepository`, starting with the ~15 methods whose body contains a predicate or an `ORDER BY`, and put the playback gate inside its scope rather than beside it.
- *Effort.* 2 hours for the query fix; about half a day for the playback-token gate including the preview decision; 2–3 days for the shared contract suite that stops it recurring.
- *Fixed 16 September, mid-review — the photograph half.* The review found the same bug on photographs, and it was the more alarming half: the interface promises `listPhotosForCatalogue(catalogueId, options?: { liveOnly?: boolean })` (`lib/db/repository.ts:343`), `lib/catalogue-cache.ts:65` calls it with `{ liveOnly: true }`, the memory driver honours it — and the Supabase driver implemented it as `listPhotosForCatalogue(catalogueId: string)`, dropping the option silently, so every photograph reached guests the instant its upload finished. TypeScript cannot catch that: a method taking fewer parameters than the interface declares is still assignable to it. It was fixed at commit `7730633` ("Guests saw unpublished photographs on the Supabase driver", 16 September 2026, 11:27) — the method now takes the option and applies `.not('live_at','is',null)` (`lib/db/supabase-repository.ts:1625-1642`), and `tests/unit/supabase-query-shape.test.ts` pins that filter through a recording stand-in client. The commit's own message says the wider finding is not fixed by the patch, which is right: the titles half above, the playback gate, and the missing conformance suite all remain open.

**H2. All alerting — and most of the background jobs — depend on a GitHub Actions scheduler that disables itself after 60 days without a commit.** Caught independently by both the deployability and scalability reviews.

- *Evidence.* `vercel.json` registers only two of the product's six cron jobs (`reconcile`, `usage`) because Vercel's free tier caps cron jobs at two (`app/api/cron/notify/route.ts:19-23` records this). The other four — `lifecycle`, `notify`, `warnings`, `synthetic` — run off `.github/workflows/notify-drain.yml` and `synthetic-check.yml` instead, and that workflow's own header states the rule: "a public repository's schedules are disabled after 60 days with no commits." `lib/notify/alert.ts:58` shows that alerts are *enqueued*, not sent directly — so the alerts this same system raises when something else breaks (`app/api/cron/synthetic/route.ts:97-101`, `app/api/cron/reconcile/route.ts:115-121`) are themselves delivered by the drain that has stopped.
- *Why it matters.* Sixty days without a commit is a normal gap for a one-founder pre-revenue product between sprints. When the schedule switches off, delivery emails, expiry warnings, lapse transitions and the hourly synthetic guest check all stop at once, silently, and the alert that would tell you sits undelivered in the same queue. One correction from the scalability pass matters here: the lifecycle job does **not** reclaim storage — the ladder ends at `cold` ("streaming paused, every file retained"), and the deletion job is deliberately unbuilt (`lib/lifecycle.ts:13-14`). So the real exposure isn't the storage-cost curve it first looked like — it's that a couple never receives the link to their wedding film, and the studio finds out before you do.
- *Fix.* Move the schedule off GitHub Actions — Vercel's Hobby tier caps a project at 2 cron jobs (which is why 4 of the product's 6 live on GitHub Actions today); Pro lifts that to up to 100 per project and costs $20/month per Vercel's public pricing, comfortably covering all six of the product's jobs.<sup>1</sup> Until that's paid for, add a heartbeat in the other direction inside a Vercel-scheduled route: check how stale the last `notify` job run is, and when it's more than two hours overdue, send directly rather than through the queue.
- *Effort.* 1 hour to move the schedule once Pro is on; 3 hours for the interim heartbeat if it's needed first.

<sup>1</sup> Verified 16 September 2026: [Vercel pricing](https://vercel.com/pricing) ($20/mo Pro); [Cron Jobs: Usage & Pricing](https://vercel.com/docs/cron-jobs/usage-and-pricing) (Hobby: 2 jobs/project, once-daily; Pro: up to 100 jobs/project, per-minute).

### Medium severity — 18 findings

**M1. Only 2 of ~20 Supabase column maps are held to their schema by a test; the most-edited entity's map is untested; one comment claims a test that doesn't exist.** `TITLE_COLUMNS` and `PHOTO_COLUMNS` are exported specifically so `tests/unit/supabase-mapping.test.ts` can check them against the schema; the comment on `NOTIFICATION_COLUMNS` (`lib/db/supabase-repository.ts:111`) claims the same protection but that test file never imports it. The catalogue map — 35 fields, the single most-edited entity in the product — is a private inline object nothing can reach (`lib/db/supabase-repository.ts:239-275`). *Downgraded from high*: the verifier diffed both maps against their schemas and found nothing is actually dropped today — the risk is preventive, the same class as a real incident this file's own header describes (a storage-cap column silently unmapped for weeks). *Fix*: export the catalogue map and five others the same way, generalise the mapping test into a table-driven one, and add the reverse (read-side) assertion the write-side test can't catch. *Effort*: 1–1.5 days.

**M2. `pnpm lint` never sees `middleware.ts`, and CLAUDE.md's own table says it does.** Caught independently by the maintainability and documentation reviews. `next lint` (what `pnpm lint` runs) only scans `app/`, `components/`, `lib/`, `pages/`, `src/` by default — `modules/`, `themes/` and `middleware.ts` are invisible to it. Running eslint directly against those paths turns up four real `no-restricted-properties` violations, all in `middleware.ts:23,34,74` (reading `process.env` outside `lib/env.ts`, which CLAUDE.md's first enforced rule says can't happen). The reads themselves are justified and documented — `lib/env.ts` is `server-only` and can't be imported into edge middleware — so the code is fine; the enforcement claim is not. *Correction*: re-running lint directly against `modules/` and `themes/` today finds them clean, so the moat itself isn't currently exposed — only `middleware.ts`, and only for non-secret routing flags. *Fix*: widen the lint script's directory list (or migrate off `next lint`, which is deprecated for Next 16 anyway) and either fix or deliberately exempt the four `middleware.ts` reads. *Effort*: 2–3 hours.

**M3. `components/admin` — 3,564 lines, the console a studio actually uses — sits at 17% test coverage, and the four biggest components in it have no test at all.** `CreateWizard.tsx` (1,006 lines), `CustomizerShell.tsx` (765), `ThemeStudio.tsx` (613) and `PreviewPane.tsx` (472) have zero component tests; only 602 of `components/admin`'s 3,564 lines are covered (the wider `components/` tree, 13,326 lines including the better-tested guest-facing streaming components, aggregates to 37%). E2E covers the happy path well (30 tests across the customizer and console) but every admin spec skips mobile width, so the console — which CLAUDE.md's own definition of done requires to work live in front of a planner — has no automated coverage at phone width. This is the inverse of where the risk actually sits: the pure logic (schema, i18n, entitlements) is at 92–100%; the screens holding the product's actual differentiator are at 17%. *Fix*: not a coverage-number chase — add tests for the four state machines whose bugs are invisible until someone looks (`CustomizerShell`'s undo/redo/autosave, `CreateWizard`'s draft restore, `UploadManager`'s retry path, `ModuleRenderer` against a stale module type), and drop the mobile skip from one cheap admin spec. *Effort*: 3–4 days for the four suites; half a day for the mobile spec.

**M4. `CreateWizard` is 1,006 lines with 26 `useState` calls in the component itself, and its draft-restore silently drops several fields on an early reload.** `create()` performs two sequenced network calls with four inline response casts; `chooseStyle` mutates five other pieces of state as a side effect. The local-storage draft mirror only restores 5 of roughly 11 relevant fields, so a refresh on step 1 or 2 silently loses occasion, timezone, premiere date, privacy and the couple's email — nothing fails, nothing is logged, no test covers it. *Correction*: the original count of "29 useState hooks" mixed in a separate sub-component and an import line; the wizard itself has 26. *Fix*: collapse the state into one `useReducer`, move `create()` into a testable module, replace the inline casts with a small schema-validated `postJson` helper, and split the five wizard steps into their own files. *Effort*: 2–3 days.

**M5. Org-scoping has no automated test — it currently holds 100%, which is exactly why now is the cheapest moment to pin it.** `lib/admin/session.ts` states the strong claim that "a route that does not call one of these functions is visibly unscoped," but nothing in `tests/` checks it, unlike the much lower-stakes module-type rule, which gets a 35-line filesystem-walk test. The verifier re-audited and confirmed every route does call one of the guard functions today. *Correction*: the proposed test needs care — the reviewer's route/handler counts were off (34 route files, 46 handlers, not "49 non-platform plus 11 platform"), and a naive version would fail on day one against `page.tsx` files, which use different guard names (`getOperatorSession`, `getSessionOrg`, `getEditableCatalogue`) than the API routes do. *Fix*: a filesystem-walk test in the shape of the existing module-registry one, covering both guard-name families and an explicit allowlist for the handful of deliberately public pages (login, register, new). *Effort*: 2 hours, plus care in getting the route/page distinction right.

**M6. The guest page isn't actually ISR-cached, and the capacity plan assumes it is.** `app/c/[slug]/page.tsx:21` declares `revalidate = 3600`, but the page reads cookies unconditionally (`lib/guest-locale.ts:22-23`, plus the passcode check) and awaits `searchParams` — three separate things that each force a Next.js page out of static rendering. `docs/SCALE-PLAN.md` rests its headroom arithmetic on "300 guests hitting one link mostly hit the edge cache" — the code doesn't do that; every guest render is a live function invocation. *Correction*: the runtime cost is smaller than first framed — the underlying data is still cached (`lib/catalogue-cache.ts`), so this is cheap Node invocations against Vercel's million-a-month allowance, not a wedding-evening failure. What's actually broken is the planning document, and it's a document Sandeep would use to judge whether the stack holds. *Fix*: correct `docs/SCALE-PLAN.md` now; separately, move the passcode/locale decision into `middleware.ts` (which already runs on every request) so the page itself can render statically. *Effort*: half a day for the doc fix; 3–5 days for the static-shell rework, and it can wait.

**M7. The 10-second playback heartbeat runs at roughly 12x the invocation budget the scale plan assumes, with 5–6 Supabase round trips per beat.** `useProgressHeartbeat.ts` posts every 10 seconds while a film plays; each post is a `force-dynamic` function doing a profile read, a title read, a progress read, an upsert and a play-event insert. At the stated 300-guests-for-20-minutes scenario that's roughly 360,000 invocations for one wedding evening against a scale-plan figure of 30,000 invocations a month for the *entire* system. *Correction*: at today's actual ~10 weddings/month this still sits inside Vercel's monthly allowance, and the worst-case query rate assumes all 300 guests watching at the exact same moment — the peak of the peak, not the norm. Real gap, gradual failure mode rather than a cliff. *Fix*: raise the heartbeat interval and batch deltas into one request; collapse the five queries into one Postgres function. *Effort*: 2–3 days.

**M8. The nightly usage-rollup cron is fully serial with no time limit, and the two reviews disagree on how much that matters.** It walks every catalogue, then every title in each, awaiting one Bunny API call at a time with no concurrency and no `maxDuration` set anywhere in the repository. At the stated ~10-weddings/month target within 12 months this becomes several hundred sequential calls inside one function invocation. The two lenses that both caught this landed in different places: the **scalability** pass kept it at medium, reasoning that the serial-fan-out mechanism itself needs fixing before catalogue count grows further, and that a killed run shows as "overdue" on the health page rather than failing invisibly. The **deployability** pass corrected it down to low, because nothing downstream currently reads the usage table the job writes (`lib/db/repository.ts:395` has no callers outside the two drivers) and the "delivery alert" it's supposed to protect is a log line, not an email — so a timed-out run today costs an unread row, not lost revenue or a missed page. Both are right about the code; we're presenting this as medium because the underlying mechanism (unbounded serial fan-out, no duration limit) is the thing worth fixing regardless of whether today's consequence is small. *Fix*: set `maxDuration`, run the per-title calls in bounded parallel, and give the catalogue walk a resumable cursor. *Effort*: 4 hours.

**M9. No staging environment — a migration and the build that needs it meet for the first time in production.** This is already tracked as N-87 in `docs/NEXT.md`, labelled "debt that is costing us." Vercel Preview has no real environment variables, and `lib/env.ts` refuses to boot a production-shaped build on an ephemeral data driver, so no preview deployment can currently run against anything real. The 212-test E2E suite proves nothing about the combination that actually breaks, because it only ever runs against the memory and fake drivers. *Fix*: exactly as N-87 specifies — a second free-tier Supabase project seeded from the demo fixture, a second Bunny library, a staging subdomain, and the deploy script pointed at it first. *Effort*: 1 day plus two free accounts.

**M10. No migration ledger — schema changes reach production by pasting SQL into a web console, and nothing can currently answer "is production on head?"** `scripts/migrate.ts` only prints filenames; it applies nothing. The two things that could answer the question are both already stale — a health probe still calls the credits table "the newest migration's table (0021)" while migration 0025 is head. `docs/NEXT.md` already records one incident: applying migrations by hand broke catalogue creation for several minutes on 12 September. *Fix*: add a real `schema_migrations` table and rewrite `scripts/migrate.ts` to connect, read it, and apply only what's missing, each in its own transaction; have the health endpoint report the applied version. *Effort*: 1 day.

**M11. The one automated proof that a deploy actually landed checks a hostname that isn't production, and the deployment docs name three different domains.** Caught independently by the deployability and documentation reviews. The ship ritual's verification step curls `marquee-film-pub.vercel.app` — a legacy Vercel project alias — while production is `mehfilbox.com`; `docs/DEPLOYMENT.md` separately states the production domain is `heirloomfilms.in`, a third name. This isn't hypothetical: `docs/PROGRESS.md` already records that renaming the Vercel project once orphaned this exact alias, which kept silently serving a stale build. *Correction*: the more alarming framing ("reports success for a deploy that went nowhere") overstates the common case — a genuinely stale alias would show a version mismatch and fail loudly, not pass silently; the real gap is that the canonical domain is never checked at all. *Fix*: point the verification step at the deployment URL the deploy script itself just printed, compared against the commit hash, and fix the three domain mentions in the docs to agree. *Effort*: 1 hour.

**M12. ## 4. Scalability: what breaks first

The architectural choice that matters most for scale is already made and made well: the application is never in the path of the video or photo bytes themselves (§2). That property doesn't degrade with catalogue count, and no implementation language changes it — it's the reason the findings below are about database rows and function invocations, not about streaming capacity.

## 5. Deployability and operations

The operational tooling here is genuinely ahead of a pre-revenue product's usual stage (§2): configuration fails at boot rather than at a guest's first click, a pre-deploy script catches the specific CDN misconfigurations that have actually happened before, and an hourly synthetic check walks a real guest journey against production. That's the strong half.

The weak half is what happens *around* a deploy rather than in the code being deployed:

- **The single biggest operational risk is H2** — alerting and four of six background jobs depend on a scheduler (GitHub Actions) that turns itself off after 60 days of repository inactivity, a genuinely normal gap for a solo founder between sprints. When it does, the failure is invisible by construction: the alert that would say so is delivered by the same queue that stopped.
- **There is no staging (M9).** Every migration and every build meet each other for the first time in production. This is the reason several of the other findings in this document exist at all — each one is a class of bug a staging run would have caught before it shipped, not after.
- **There is no migration ledger (M10).** Nothing in the repository can currently answer "is production on head?" without a human checking by hand, and the two automated things that gesture at an answer are already out of date.
- **The one automated proof a deploy landed checks the wrong host (M11)**, a direct legacy of a Vercel project rename, with the deployment docs themselves naming three different production domains.

None of these are exotic — they're the standard gaps a fast-moving pre-revenue product accumulates before its first real operational incident forces the issue. The difference here is that three of the four (H2, M9, M10) are already named in the project's own backlog or documentation as known debt; this assessment mainly confirms the size of each and re-prices the fix. The remaining low-severity operational findings (deploy-script quoting, secret rotation, the untested Docker path, `/api/health`'s always-green response) are all real and all cheap — see the Deployability table in §3 — but none of them is where an actual incident is likely to start.

## 8. What a rewrite would and would not fix

A rewrite would not fix either of the two high-severity findings — H1 is a missing test, a dropped line of query logic and an unguarded token route, H2 is a scheduling dependency, and both are cheap to fix in the code that exists today (the photograph half of H1 was fixed in two hours on 16 September, which is the whole argument in miniature). It would not improve the three properties actually carrying the product's risk profile: the byte-free media path (§2) is an architecture decision independent of language and a new codebase would make the same choice or a worse one; the module-boundary and authorization enforcement (§2) exist because someone wrote filesystem-walking tests for them, which a rewrite would have to reproduce from scratch to keep the same guarantee, not inherit for free. What a rewrite plausibly *would* address is the concentration of risk in five files — two 1,000+-line drivers and three or four large admin components (§1, §3 M1–M5) — but a targeted refactor of exactly those files reaches the same place without re-implementing everything around them, and without the months of parity risk a full rewrite carries on a product that needs to keep shipping. The documentation debt (§6) and the operational gaps (§5) are organisational, not architectural; they would follow a rewrite unchanged unless someone fixed them separately either way. The full cost comparison — including the option of porting to a different language or platform rather than staying in TypeScript — is in [03-port-and-build-vs-buy.md](03-port-and-build-vs-buy.md).
